# Public paired release benchmark — 28 October 2026

This report compares the 0.8 candidate engine at `345f42ee0ed906620e9a11a8e135045f034df553` with public 0.7.0 at `9a852d2`. It measures fresh native searches, with the optional adaptive strategy off. It does not measure browser session continuity, manual editing, saved-incumbent selection or the new order-cost workflow.

**All 636 scored layouts passed saved independent validation.** No search or validator failures and no `too_long` losses occurred. The full suite is complete.

On the 300 ordinary-open Lectra tasks, **0.8 is slightly worse than 0.7 in this run**: mean **-0.0179 pp**, median **-0.0004 pp**, **47 wins / 187 ties / 66 losses**. Most pairs tie. These small differences in one wall-clock run do not establish a durable regression, but they do not show a broad improvement either.

Against Lectra, 0.8 has mean **-1.3914 pp**, median **-1.5709 pp**, **77 wins / 12 ties / 211 losses**. Dense markers remain weak: in the 151+ piece / 75-85% reference stratum, all 25 cases lose to Lectra. The new result is numerically worse than the historical 20 October headline; different engine revisions, effective process priority and shared load prevent attributing that difference to one cause.

Across 18 garment jobs, useful-yield change is mean **+3.5692 pp**, median **+0.0073 pp**, **8 wins / 7 ties / 3 losses**. The mean is driven by the three open/start-defect gains: mean **+15.5215 pp**, median **+14.4622 pp**, **3 / 0 / 0**. It must not be presented as a typical improvement across garments. Clean folded jobs tie. Clean tube jobs have mean **-0.1590 pp**, median **-0.0071 pp**, **0 / 2 / 1**. Simon clean tubular, folded-with-defect and tubular-with-defect regress; every paired garment value is below.

## Method

The Lectra input is the exact frozen 300-task conversion used for the 20 October report. Its SHA-256 is `66edbac7fcb1baa57945147a99113b7449f262d928012d43385847d039849c8c`. No tasks were replaced or selected by score. There are 296 Tier A tasks and four Tier B-only tasks. Tier B includes Tier A. The sample balances 12 piece-count/reference-efficiency strata, 25 tasks each. It is unweighted and is not a population estimate.

Both engines receive the same saved jobs, seed 1, one run, 60-second search budget, 80% exploration / 20% compression profile, four concurrent tasks and three requested search workers per task. There are at most 12 search workers, plus coordinator/helper threads. The driver is launched with `nice -n 10` and also prefixes each engine with `nice -n 10`. The measured effective engine priority is therefore nice 19 (the Linux cap), equally for both engines. This is lower priority than the historical nice-10 run and is a recorded scheduler difference; search settings, budgets and thread counts are unchanged. No engine builds run during the timed search stages. The 300 tasks are split into fixed consecutive blocks of 20. Each block runs both engines before the next block. Engine order alternates by block: 0.7 first in even blocks, 0.8 first in odd blocks. The final odd block count gives 0.7 eight first blocks and 0.8 seven. This reduces broad load drift; it does not match instantaneous CPU availability.

The added FreeSewing matrix has 18 jobs: Simon shirt, Teagan T-shirt and Titan trouser block, each open / folded / tubular and clean / start-defect. They retain the MIT fixture notices, quantities, grain, mirror rules, zero gaps and S1 M2 L2 XL1 ratio. Open width is 1500 mm; folded/tubular table width is 750 mm, with two layers. Teagan front/back get centre-line fold declarations in the two-layer variants, using the established fixture conversion. Simon and Titan keep their source declarations. These two-layer cases are diagnostic hypothetical lays, not a recommendation to cut each garment that way. The defect is an original synthetic 20 × 20 mm square at the fabric start; the reserved prefix remains in the marker length. Both engines use the same generated inputs. The matrix runs 0.8 first, then 0.7, four tasks at a time. These are 60-second runs; the historical 300-second garment results are not refreshed.

Occupied efficiency is the physical cut-footprint area divided by table width and marker length. Useful yield counts full copies that serve the garment order, excludes surplus and divides by fabric area across all layers. These measures can differ on folded/tubular lays. The tables show both, plus length and surplus. Useful yield comes from the independent validator's geometry-based calculation; it is checked against the saved result. Do not judge two-layer jobs by occupied efficiency alone.

Differences are 0.8 minus 0.7, or BETA minus Lectra, in percentage points. Positive is better. A tie is within 0.1 pp, inclusive. Mean and median use valid pairs only. Failed cases stay in attempted counts and are listed without fabricated numeric scores. No reruns are selected by score. Whole-call times include construction and evidence work; independent validation time is also recorded. A requested 60-second search is not a hard 60-second process deadline.

## Reproduce

Build the unmodified CLI in each public source export. Give each export its own fresh `CARGO_TARGET_DIR`; do not share target directories across archived versions. Keep output outside the source. From each `marker/` directory:

```sh
cargo build --locked --release -p beta-marker-cli --bin beta-marker
```

Save the two executables as `ROOT/bin/beta-marker07` and `ROOT/bin/beta-marker08`. Keep the exports at `ROOT/source07` and `ROOT/source08`. Build the orchestration tool from this branch:

```sh
cargo build --locked --release --manifest-path bench/public/Cargo.toml --bin beta-launch8-bench
beta-launch8-bench prepare ROOT/source08/marker PUBLIC_INPUTS/sample-300.jsonl ROOT/out
nice -n 10 beta-launch8-bench run ROOT
beta-launch8-bench summarize ROOT ROOT/source08/marker/apps/site/data/benchmark
```

Use a fresh `ROOT/out`. `prepare` checks the frozen input checksum, generates shared replay inputs and fixes the engine order before scores exist. `run` refuses existing result folders. `summarize` requires all stages complete and verifies the saved independent validation evidence before exporting. Geometry-free website files go to `ROOT/out/site`; the paired aggregate goes to `ROOT/out/summary.json`. On Windows add `.exe` to executable names; timed engines in this report ran on Linux.

## Limits

Sheet type 0 is assumed to mean an ordinary open rectangular strip, and `flip_x` is assumed to reflect the x coordinate before rotation. The source codebook, finite-sheet denominator details, Lectra version/hardware/thread count and exact stopping rule remain unverified. Unsupported source constraints and unverified rings remain excluded. None of these assumptions was changed to improve the new score.

Equal search budgets and thread counts do not guarantee equal executed work on shared hardware. Fixed seeds do not make wall-clock searches deterministic. One seed and one run per engine/task do not estimate run-to-run variance or statistical significance. The 18 garment jobs reuse three pattern families; they are not 18 independent garment designs. The paired comparison isolates source revision more closely than the old server-versus-laptop comparison, but it still carries load and scheduling noise. Small changes need repeat runs before treating them as durable gains.

The historical 20 October results used an older engine revision, not 0.7.0. They remain visible under their original IDs and version labels. This new comparison does not re-run the 60-task matched-duration suite or academic instances. No general win over Lectra, Gerber, Optitex or Tukatech follows from this test.
